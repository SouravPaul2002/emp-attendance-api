# REVIEW.md

| # | Where (function / line) | What is wrong | How you'd notice it (test, input, or symptom) | How you fixed it |
|---|---|---|---|---|
| 1 | health (lines 72–74) | The health check returned 200 even when MongoDB was down. | Stop MongoDB or pass a bad port; GET /health still gave 200. | I added a ping command to MongoDB and raised a 503 if it fails. |
| 2 | create_employee (lines 79–85) | Two concurrent requests with the same emp_code could both pass find_one and insert duplicates. | Sending two requests at the same time with the same emp_code created two employees or caused a 500 error. | I added a unique index on emp_code and caught DuplicateKeyError to return 409. |
| 3 | EmployeeIn (lines 53–61) | The model did not validate the emp_code pattern, email format, string lengths, or ensure shift_start differs from shift_end. | Posting an invalid employee code like bad or setting shift_start equal to shift_end returned 201 instead of 422. | I added regex patterns, length limits, and a model validator in Pydantic. |
| 4 | create_employee (line 82) | created_at was saved as a naive local datetime and returned as a string instead of epoch milliseconds. | The POST /employees response had a string or datetime for created_at instead of an integer. | I saved UTC datetimes in MongoDB and converted them to epoch milliseconds in the response. |
| 5 | list_employees (line 93) | The offset calculation was page * page_size, which skipped the first page when page was 1. | Calling GET /employees?page=1 returned items starting at index 20 instead of the first 20. | I changed the offset formula to (page - 1) * page_size. |
| 6 | list_employees (line 94) | The total count was calculated on the entire collection instead of the filtered query. | Calling GET /employees?department=Sales returned the count of all employees in the company. | I passed the query filter into count_documents. |
| 7 | list_employees (line 95) | The results were not sorted by emp_code ascending. | The list came back in natural MongoDB order rather than sorted by emp_code. | I added an ascending sort on emp_code to the query cursor. |
| 8 | punch_in (lines 101, 113) | If the employee code did not exist, emp was None and caused an unhandled TypeError when reading shift times. | Punching in with an unknown emp_code crashed with a 500 error instead of returning 404. | I checked if the employee document exists and raised a 404 if it does not. |
| 9 | punch_in (lines 104–118) | Two simultaneous punch-ins for the same employee on the same date could both succeed. | Sending two punch-in requests at the same time created two attendance logs for the same day. | I added a unique compound index on (emp_code, date) and caught DuplicateKeyError to return 409. |
| 10 | punch_in (lines 102–103) | It used UTC dates directly, did not truncate seconds, and missed the overnight shift rule. | Punching in at 01:00 for an overnight shift assigned the record to today's date instead of the previous day's shift. | I converted the timestamp to IST, truncated whole seconds, checked overnight shift rules against shift_end, and saved UTC datetime. |
| 11 | PunchInIn / punch_in (lines 66, 109) | The status field accepted arbitrary strings instead of allowed presence statuses. | Punching in with status LEAVE or ABSENT gave 201 instead of 422. | I restricted the status field in Pydantic to PRESENT, WFH, and ON_DUTY. |
| 12 | punch_in and list_attendance (lines 119–120, 148–150) | Leaked internal MongoDB _id as id and returned raw datetimes instead of epoch milliseconds. | Responses contained an id field and ISO date strings instead of integer millisecond timestamps. | I removed the id field and converted all datetime values to integer milliseconds in the serializer. |
| 13 | compute_late_minutes (lines 33–37) | It floors minutes before checking > 10, and it uses .replace() on the punch-in date instead of converting to IST or checking overnight shifts. | Punching in at 09:40:01 for a 09:30 shift returned 0 instead of 10, and non-IST times had their shift start set on the wrong day. | I converted punch-in to IST, checked whether elapsed seconds are greater than 600, and floored minutes from shift start when late. |
| 14 | compute_work_hours (lines 40–41) | Python's built-in round() uses round-half-to-even instead of round-half-up. | A duration that produced 2.525 rounded to 2.52 instead of 2.53. | I switched to Python's Decimal class with ROUND_HALF_UP. |
| 15 | compute_overtime (lines 44–47) | It counted overtime below the 30-minute threshold, failed on overnight shifts, and compared naive with aware datetimes. | Punching out 10 minutes after shift end gave 10 minutes overtime instead of 0, and overnight shifts raised a TypeError. | I computed the difference from shift end in IST, handled next-day shift ends for overnight shifts, and ignored overtime under 30 minutes. |
| 16 | list_attendance (lines 144–150) | The query loaded all attendance records into memory and sorted them in Python. | The starter calls list(find(q)) into memory and then sorts the entire list with Python's sorted() function. | I replaced the Python sort with cursor-level sorting and pagination in MongoDB. |
| 17 | list_attendance (lines 127–128) | It did not validate date ranges where date_from is greater than date_to. | Sending date_from=2026-07-10 and date_to=2026-07-01 returned 200 with an empty list instead of 422. | I added a check that raises 422 if date_from is after date_to. |
| 18 | PunchInIn.punched_at | Timestamps had no range checks, accepted strings and floats, and if body.punched_at treated 0 as missing. | Sending punched_at as a string like 1783312500000, a float, a small number like 1783312500, or 0 returned 201 instead of 422. | I used StrictInt with range limits between 100000000000 and 4102444800000, and checked is not None instead of truthiness. |
| 19 | Date and status validation across endpoints | Non-existent dates like 2026-02-30 passed the regex and crashed with a 500, and the status filter accepted any string. | Sending joined_on as 2026-02-30 crashed with 500, and querying ?status=INVALID returned 200 instead of 422. | I added a date validator that raises 422 on invalid calendar dates and restricted the status parameter to allowed values. |
| 20 | Pagination parameters (list_employees, list_attendance) | The page and page_size query parameters were not bounded. | Requesting ?page=0 or ?page_size=500 was accepted instead of returning 422. | I added minimum 1 on page and maximum 100 on page_size. |

### Looked at and left alone
- work_hours and punch_out set to null on punch-in: I checked whether these should have defaults, but the spec says open records must have null.
- ABSENT and LEAVE records with null punch times: These records do not store punch-in or punch-out, which matches the data model.
